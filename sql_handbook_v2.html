01 SQL Fundamentals

The vocabulary every interview assumes you already own: what a database engine guarantees, how data is structured, and the hidden order in which a query actually runs.

DBMS vs RDBMS

Definition
A DBMS (Database Management System) is software that stores, retrieves and manages data. An RDBMS is a DBMS where data is organized into relations (tables) with defined relationships, enforced via keys and constraints, and queried with SQL. Examples: PostgreSQL, MySQL, SQL Server, Oracle. Non-relational DBMS include MongoDB (document), Redis (key-value), Cassandra (wide-column).
AspectDBMS (generic / file-based)RDBMS

RelationshipsNot enforcedEnforced via PK/FK
IntegrityApp-levelConstraints + ACID transactions
Query languageProprietary / noneSQL
Multi-userLimitedConcurrency control, isolation

ACID properties

Definition
The four guarantees a transaction provides so that concurrent, partial, or interrupted work never corrupts data.
  • Atomicity — all statements in a transaction succeed together or none do. A failed step rolls the whole unit back.
  • Consistency — every committed transaction moves the database from one valid state to another, never violating constraints.
  • Isolation — concurrent transactions don't see each other's uncommitted work; the result is as if they ran in some serial order. Controlled by isolation levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable.
  • Durability — once committed, data survives crashes (written to disk / WAL).
Isolation levelDirty readNon-repeatable readPhantom read
Read UncommittedPossiblePossiblePossible
Read CommittedNoPossiblePossible
Repeatable ReadNoNoPossible*
SerializableNoNoNo

*PostgreSQL's Repeatable Read (snapshot isolation) also prevents phantoms in practice.

Interview
  1. "Explain ACID with a bank transfer." Debiting account A and crediting account B must be atomic — if the credit fails, the debit is rolled back, so money is never lost or created. Isolation keeps a concurrent balance-check from reading a half-finished transfer.
  2. "Difference between non-repeatable read and phantom read?" Non-repeatable: the same row returns different values on re-read. Phantom: a re-run query returns a different set of rows (new rows appeared) due to inserts by another transaction.

Tables, rows, columns

Definition
A table (relation) is a named set of rows. A column (attribute/field) has a name and a data type. A row (record/tuple) is one observation. The set of valid values for a column is its domain. Relational theory says row order and column order carry no meaning — never rely on physical order.

Primary Key & Foreign Key

Definition
A Primary Key (PK) uniquely identifies each row: it must be unique and NOT NULL. A Foreign Key (FK) is a column (or set) in one table that references the PK of another, enforcing referential integrity — you can't reference a department that doesn't exist.
SQL · keys
CREATE TABLE departments (
  dept_id   INT PRIMARY KEY,
  dept_name VARCHAR(60) NOT NULL
);

CREATE TABLE employees (
  emp_id     INT PRIMARY KEY,
  name       VARCHAR(80) NOT NULL,
  dept_id    INT REFERENCES departments(dept_id) ON DELETE SET NULL,
  manager_id INT REFERENCES employees(emp_id),   -- self-reference
  salary     NUMERIC(10,2) CHECK (salary >= 0)
);
  • Composite key: a PK made of multiple columns, e.g. (order_id, line_no).
  • Natural key: a real-world identifier (email, SSN). Surrogate key: a meaningless system-generated id (auto-increment / identity / sequence).
  • ON DELETE / ON UPDATE actions: CASCADE, SET NULL, RESTRICT, NO ACTION.

Best practice
Name your constraints (CONSTRAINT chk_salary_pos CHECK (...)). Named constraints produce readable errors and can be altered/dropped by name later.

NULL & three-valued logic

Definition
NULL means unknown / not applicable — it is not zero and not an empty string. Because a value can be unknown, SQL uses three-valued logic: every predicate is TRUE, FALSE, or UNKNOWN. Only rows where the WHERE clause is TRUE are returned.
SQL · null behaviour
NULL = NULL        -- UNKNOWN  (NOT true!)
NULL <> 5         -- UNKNOWN
5 + NULL           -- NULL
NULL OR TRUE       -- TRUE
NULL AND FALSE     -- FALSE

-- Correct null tests:
WHERE col IS NULL
WHERE col IS NOT NULL
COALESCE(col, 0)            -- first non-null
NULLIF(a, b)               -- NULL if a = b, else a
Pitfall
WHERE col = NULL returns nothing — it evaluates to UNKNOWN. Always use IS NULL. Also: COUNT(col) skips NULLs but COUNT(*) counts every row; SUM/AVG ignore NULLs; and NOT IN (subquery with a NULL) silently returns zero rows.
Interview
  1. "What does SELECT COUNT(commission) FROM employees return if some commissions are NULL?" Only the count of non-NULL commissions.
  2. "Why might WHERE dept_id NOT IN (SELECT dept_id FROM x) return nothing?" If the subquery contains a NULL, the comparison becomes UNKNOWN for every row. Use NOT EXISTS instead.

SQL logical execution order

Definition
You write a query starting with SELECT, but the engine logically evaluates it in a different order. Knowing this explains why you can't use a SELECT alias in WHERE, and why WHERE filters before grouping while HAVING filters after.
logical processing order
1.  FROM / JOIN      -- build the row source, resolve joins
2.  ON               -- join predicates
3.  WHERE            -- filter individual rows (no aggregates, no aliases)
4.  GROUP BY         -- collapse rows into groups
5.  HAVING           -- filter groups (can use aggregates)
6.  SELECT           -- compute expressions, window functions, assign aliases
7.  DISTINCT         -- remove duplicate output rows
8.  ORDER BY         -- sort (CAN use SELECT aliases)
9.  LIMIT / OFFSET   -- slice the result
Interview
  1. "Why can't I filter on a column alias in WHERE but I can in ORDER BY?" Because WHERE (step 3) runs before SELECT (step 6) where the alias is created, while ORDER BY (step 8) runs after.
  2. "WHERE vs HAVING?" WHERE filters rows before aggregation; HAVING filters aggregated groups. Push every non-aggregate filter into WHERE so fewer rows reach GROUP BY.
Rules Summary — SQL Fundamentals
🧱 Structural Rules
  • Statements end with a semicolon ; — required in multi-statement scripts and most CLI clients.
  • SQL keywords are case-insensitive; use UPPERCASE for keywords and snake_case for identifiers consistently.
  • Identifiers matching reserved words must be quoted: "order", `date`, or [group] depending on dialect.
🔢 NULL Rules
  • NULL means unknown — not zero, not empty string, not equal to itself. Always use IS NULL / IS NOT NULL.
  • Any arithmetic or comparison with NULL returns NULL: NULL + 5 → NULL, NULL = NULL → UNKNOWN.
  • Three-valued logic: TRUE, FALSE, UNKNOWN — WHERE discards UNKNOWN rows (treats them as FALSE).
  • Aggregate functions (SUM, AVG, COUNT(col) etc.) silently skip NULLs; COUNT(*) does not.
📋 Execution Order Rules — the most important rule set in SQL
  • Fixed logical order: FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  • Window functions execute after HAVING but before ORDER BY — allowed only in SELECT and ORDER BY.
  • SELECT aliases are invisible in WHERE, GROUP BY, and HAVING — only usable in ORDER BY (engine-dependent).
  • You cannot reference an aggregate function in WHERE — use HAVING instead.
❌ Illegal Operations
  • Do not compare to NULL with = or != — always use IS NULL / IS NOT NULL.
  • Do not use aggregate functions in WHERE — place them in HAVING.
  • Do not reference a SELECT alias in WHERE, GROUP BY, or HAVING — they do not exist yet at those stages.

02 Data Types

Choosing the right type controls storage, correctness, and performance. Wrong types are the silent cause of rounding bugs, overflow, and unindexable predicates.

Numeric types

CategoryTypesNotes
IntegerSMALLINT, INT/INTEGER, BIGINTExact; pick by range. BIGINT for surrogate keys at scale.
Exact decimalNUMERIC(p,s) / DECIMAL(p,s)Exact precision — always use for money.
ApproximateREAL, FLOAT, DOUBLEBinary floating point; rounding errors. Never for currency.
SerialSERIAL/IDENTITY/AUTO_INCREMENTAuto-generated surrogate keys.
Pitfall
0.1 + 0.2 <> 0.3 in FLOAT. Store prices as NUMERIC(12,2). Also watch integer division: 5 / 2 = 2 in many engines — cast one side: 5 / 2.0 or CAST(5 AS NUMERIC)/2.

Character types

  • CHAR(n) — fixed length, space-padded. Use only for truly fixed codes.
  • VARCHAR(n) — variable up to n. The everyday string type.
  • TEXT / CLOB — large, unbounded text. PostgreSQL TEXT and VARCHAR perform identically.

Boolean

Definition
A true/false/unknown(NULL) type. PostgreSQL has native BOOLEAN. SQL Server uses BIT (0/1). MySQL BOOLEAN is an alias for TINYINT(1).

Date & timestamp types

TypeStores
DATECalendar date (no time)
TIMETime of day
TIMESTAMPDate + time, no zone
TIMESTAMPTZ / TIMESTAMP WITH TIME ZONEInstant in UTC, zone-aware — preferred for events
INTERVALA duration (e.g. INTERVAL '7 days')

Binary & semi-structured

  • BYTEA / BLOB / VARBINARY — raw bytes (rarely store large blobs in the DB; keep a pointer).
  • JSON / JSONB / VARIANT — semi-structured. PostgreSQL JSONB is indexable; Snowflake uses VARIANT.
  • ARRAY, STRUCT, MAP — nested types in Spark SQL / BigQuery / Snowflake.
  • UUID — 128-bit identifier.

Type conversion & casting

SQL · casting
CAST(amount AS NUMERIC(10,2))      -- ANSI standard, portable
amount::NUMERIC(10,2)               -- PostgreSQL shorthand
CONVERT(VARCHAR, order_date, 23)    -- SQL Server, with style code
TRY_CAST('abc' AS INT)              -- returns NULL instead of error (SQL Server / Snowflake)
TO_DATE('2024-01-15','YYYY-MM-DD')  -- string -> date

Implicit vs explicit: implicit conversion happens automatically (INT compared to BIGINT); explicit is when you call CAST. Implicit conversion is where indexes silently stop being used.

Best practice
Match the type of a literal to the column it's compared against. Comparing an indexed VARCHAR code to an integer literal forces an implicit cast on every row and disables the index.
Interview
  1. "Why never store money as FLOAT?" Binary floating point can't represent most decimals exactly, so sums drift. Use NUMERIC/DECIMAL.
  2. "DATE vs TIMESTAMP vs TIMESTAMPTZ — which for an event log?" TIMESTAMPTZ (store UTC), so events from different zones are comparable and DST-safe.
Rules Summary — Data Types
🔢 Numeric Rules
  • Use the smallest type that safely covers your range: SMALLINT → INT → BIGINT — smaller types are faster and use less storage.
  • Use DECIMAL / NUMERIC for money and exact values — never FLOAT or DOUBLE (binary floating-point drift corrupts financial calculations).
  • Use DECIMAL(precision, scale) where precision = total digits, scale = decimal places: DECIMAL(12,2) for currency.
📝 String Rules
  • VARCHAR(n) allocates only what is needed (up to n); CHAR(n) always pads to n — use VARCHAR for most string columns.
  • In MySQL, use VARCHAR not TEXT for columns you need to index directly (TEXT columns require a length prefix for indexing).
  • String comparisons in PostgreSQL are case-sensitive; in MySQL they depend on the collation — standardize with LOWER() or a case-insensitive collation.
📅 Date & Time Rules
  • Store all event timestamps as TIMESTAMPTZ (TIMESTAMP WITH TIME ZONE) in UTC; convert to local time only at display.
  • Use DATE for calendar dates (no time), TIMESTAMP for naive datetimes, INTERVAL for durations.
  • TIMESTAMP and TIMESTAMPTZ are different types — comparing them without a cast can produce silent timezone errors.
🔄 Casting Rules
  • Always prefer explicit casts: CAST(col AS type) or col::type — implicit casts are dialect-specific and can silently produce wrong results.
  • Implicit casts on indexed columns in WHERE make the predicate non-sargable and disable the index.
  • Casting a wider type to a narrower one (e.g. BIGINT → INT) can overflow — validate the range first.
❌ Illegal Operations
  • Never store money as FLOAT or DOUBLE — use DECIMAL(p,s).
  • Do not compare a DATE to a TIMESTAMP without explicit casting — behavior is dialect-dependent.
  • Do not assume VARCHAR(MAX) / TEXT columns can be indexed with a standard B-tree — length prefix restrictions apply.

03 DDL · DML · DQL · DCL · TCL

SQL statements split into five families. Knowing which family a command belongs to tells you whether it auto-commits, can be rolled back, or needs special privileges.

DQLQuery dataSELECTn/a (read)
DCLPermissionsGRANT, REVOKEYes

DDL — CREATE · ALTER · DROP · TRUNCATE

SQL · DDL
CREATE TABLE orders (
  order_id    BIGINT PRIMARY KEY,
  customer_id INT NOT NULL,
  order_date  DATE NOT NULL DEFAULT CURRENT_DATE,
  amount      NUMERIC(12,2) CHECK (amount >= 0),
  status      VARCHAR(20) DEFAULT 'NEW'
);

ALTER TABLE orders ADD COLUMN channel VARCHAR(20);
ALTER TABLE orders ALTER COLUMN status SET DEFAULT 'PENDING';
ALTER TABLE orders DROP COLUMN channel;

TRUNCATE TABLE orders;     -- empties all rows, fast, resets identity
DROP TABLE orders;         -- removes the table definition entirely
DELETE vs TRUNCATE vs DROP
  • DELETE (DML) — removes rows matching a filter, logged per-row, fires triggers, can ROLLBACK, keeps the table & identity counter.
  • TRUNCATE (DDL) — removes all rows by deallocating pages; very fast, minimal logging, resets identity, usually can't be filtered, often can't ROLLBACK (MySQL), though it can in PostgreSQL/SQL Server inside a transaction.
  • DROP (DDL) — removes the table object itself.
Interview
This trio is a top-5 interview classic. Be ready to state: speed (TRUNCATE > DELETE), WHERE support (only DELETE), rollback & trigger behaviour, identity reset, and that TRUNCATE is DDL.

DML — INSERT · UPDATE · DELETE · MERGE

SQL · DML
INSERT INTO orders (order_id, customer_id, amount)
VALUES (1, 100, 49.99), (2, 101, 12.00);            -- multi-row insert

INSERT INTO orders_archive
SELECT * FROM orders WHERE order_date < '2023-01-01'; -- INSERT...SELECT

UPDATE orders SET status = 'SHIPPED'
WHERE order_id = 1;

UPDATE orders o                                       -- update from a join
SET amount = amount * 1.1
FROM customers c
WHERE o.customer_id = c.customer_id AND c.country = 'IN';

DELETE FROM orders WHERE status = 'CANCELLED';
Pitfall
An UPDATE or DELETE with no WHERE hits every row. Run the matching SELECT first, or wrap in a transaction and inspect the rowcount before COMMIT.

MERGE / UPSERT

Definition
MERGE performs insert-or-update (and optionally delete) in one statement based on whether a match exists. The backbone of incremental ETL loads.
SQL · MERGE (ANSI / Snowflake / SQL Server)
MERGE INTO dim_customer AS t
USING staging_customer AS s
  ON t.customer_id = s.customer_id
WHEN MATCHED THEN
  UPDATE SET t.name = s.name, t.country = s.country
WHEN NOT MATCHED THEN
  INSERT (customer_id, name, country)
  VALUES (s.customer_id, s.name, s.country);
SQL · UPSERT (PostgreSQL / MySQL)
-- PostgreSQL
INSERT INTO dim_customer (customer_id, name)
VALUES (100, 'Asha')
ON CONFLICT (customer_id) DO UPDATE SET name = EXCLUDED.name;

-- MySQL
INSERT INTO dim_customer (customer_id, name) VALUES (100, 'Asha')
ON DUPLICATE KEY UPDATE name = VALUES(name);

DCL — GRANT · REVOKE

SQL · DCL
GRANT SELECT, INSERT ON orders TO analyst_role;
GRANT ALL PRIVILEGES ON SCHEMA sales TO etl_role;
REVOKE INSERT ON orders FROM analyst_role;
Best practice
Grant to roles, not individual users; assign users to roles. Follow least privilege — read roles get only SELECT.

TCL — COMMIT · ROLLBACK · SAVEPOINT

SQL · TCL
BEGIN;                      -- start transaction
  UPDATE accounts SET bal = bal - 100 WHERE id = 1;
  SAVEPOINT after_debit;
  UPDATE accounts SET bal = bal + 100 WHERE id = 2;
  -- something looks wrong:
  ROLLBACK TO after_debit;  -- undo only the credit
  UPDATE accounts SET bal = bal + 100 WHERE id = 3;
COMMIT;                     -- make all surviving changes durable
Interview
"What is a SAVEPOINT?" A named marker inside a transaction; ROLLBACK TO savepoint undoes work after it without aborting the whole transaction.
Rules Summary — DDL · DML · DQL · DCL · TCL
🛠️ DDL Rules
  • DDL statements (CREATE, ALTER, DROP, TRUNCATE) are auto-committed in most databases — they cannot be rolled back in MySQL and Oracle.
  • Exception: PostgreSQL and SQL Server allow DDL inside explicit transactions.
  • TRUNCATE is faster than DELETE for removing all rows (not logged row-by-row) but cannot use a WHERE clause.
  • DROP TABLE permanently removes the schema and all data — there is no undo without a backup.
✍️ DML Rules
  • INSERT, UPDATE, DELETE participate in transactions — wrap in BEGIN / COMMIT blocks for safety.
  • UPDATE without a WHERE clause updates every row in the table.
  • DELETE without a WHERE clause deletes every row (row-by-row logged; TRUNCATE is faster for full deletes).
  • MERGE requires a source, a target, and a matching condition; each WHEN clause is optional.
🔒 TCL Rules
  • COMMIT makes changes permanent and visible to other sessions.
  • ROLLBACK undoes all changes back to the last COMMIT or SAVEPOINT.
  • SAVEPOINT creates a named rollback point inside a transaction; ROLLBACK TO SAVEPOINT rolls back only to that point without aborting the entire transaction.
  • After a runtime error, the transaction is in an aborted state — always handle errors before committing.
❌ Illegal Operations
  • Do not issue DDL inside a transaction expecting to roll it back in MySQL or Oracle — it will auto-commit.
  • Do not use TRUNCATE when you need a WHERE condition — use DELETE instead.
  • Do not use GRANT or REVOKE (DCL) inside a transaction — they take effect immediately in most engines.

04 Filtering & Conditional Logic

Everything after FROM is about narrowing, ordering, and reshaping rows. These operators appear in nearly every interview query.

WHERE vs HAVING

Definition
WHERE filters individual rows before grouping; HAVING filters groups after aggregation. HAVING is the only place an aggregate like SUM() can appear in a filter.
SQL · where + having
SELECT dept_id, COUNT(*) AS headcount, AVG(salary) AS avg_sal
FROM employees
WHERE hire_date >= '2020-01-01'    -- row filter, runs first
GROUP BY dept_id
HAVING COUNT(*) > 5;               -- group filter, runs after aggregation

DISTINCT · ORDER BY · LIMIT / TOP

SQL · shape the output
SELECT DISTINCT country FROM customers;             -- unique values

SELECT name, salary FROM employees
ORDER BY salary DESC, name ASC                       -- multi-key sort
LIMIT 10;                                            -- PostgreSQL/MySQL/Snowflake

SELECT TOP 10 name, salary FROM employees ORDER BY salary DESC;   -- SQL Server
SELECT name FROM employees ORDER BY salary DESC FETCH FIRST 10 ROWS ONLY; -- ANSI
Pitfall
LIMIT without ORDER BY returns an arbitrary, non-deterministic set of rows. Always pair them. And DISTINCT applies to the whole row, not the first column — DISTINCT a, b dedupes pairs.

CASE expressions

Definition
SQL's if/else. Returns a value per row; works in SELECT, WHERE, ORDER BY, and inside aggregates for conditional counting.
SQL · CASE
SELECT name, salary,
  CASE
    WHEN salary >= 100000 THEN 'High'
    WHEN salary >= 50000  THEN 'Mid'
    ELSE 'Entry'
  END AS band
FROM employees;

-- Conditional aggregation (pivot trick):
SELECT
  COUNT(*) AS total,
  SUM(CASE WHEN status = 'SHIPPED' THEN 1 ELSE 0 END) AS shipped,
  AVG(CASE WHEN country = 'IN' THEN amount END)        AS avg_india
FROM orders;

Boolean operators & IN · BETWEEN · LIKE

SQL · predicates
WHERE country IN ('IN','US','UK')              -- membership
WHERE amount BETWEEN 100 AND 500                -- inclusive range (>=100 AND <=500)
WHERE name LIKE 'A%'                             -- starts with A
WHERE name LIKE '_a%'                            -- 2nd char is 'a'
WHERE email LIKE '%@gmail.com'                   -- ends with
WHERE name ILIKE 'a%'                            -- case-insensitive (PostgreSQL)
WHERE phone LIKE '12\%%' ESCAPE '\'              -- literal % via escape

Wildcards: % = any number of characters, _ = exactly one character.

EXISTS · ANY · ALL

SQL · existence & quantifiers
-- EXISTS: true if the subquery returns at least one row
SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- ANY / SOME: true if comparison holds for at least one value
WHERE salary > ANY (SELECT salary FROM employees WHERE dept_id = 2);  -- > the minimum

-- ALL: true if comparison holds for every value
WHERE salary > ALL (SELECT salary FROM employees WHERE dept_id = 2);  -- > the maximum
Interview
  1. "> ANY vs > ALL?" > ANY means greater than the smallest; > ALL means greater than the largest.
  2. "IN vs EXISTS — when is each faster?" Logically similar; EXISTS can short-circuit on the first match and handles NULLs safely, IN with a small static list is fine. Prefer NOT EXISTS over NOT IN whenever NULLs are possible.
Pitfall
BETWEEN is inclusive on both ends. For a date range, BETWEEN '2024-01-01' AND '2024-01-31' can miss timestamps on the 31st; prefer order_ts >= '2024-01-01' AND order_ts < '2024-02-01'.
Rules Summary — Filtering & Conditional Logic
🔍 WHERE Rules
  • WHERE filters rows before aggregation — cannot reference SELECT aliases or aggregate functions.
  • NULL comparisons always use IS NULL / IS NOT NULL — never = NULL or != NULL.
  • BETWEEN is inclusive on both ends. For timestamps, prefer a half-open range: col >= start AND col < end.
  • Leading wildcards in LIKE '%foo' cannot use a B-tree index — avoid on large columns.
  • NOT IN with any NULL in the list returns zero rows — use NOT EXISTS instead.
⚙️ HAVING Rules
  • HAVING filters groups after GROUP BY and can reference aggregate functions.
  • HAVING without GROUP BY treats the entire table as one group.
  • Push non-aggregate conditions to WHERE for performance — fewer rows reach GROUP BY.
📐 CASE Rules
  • CASE is an expression (not a statement) — it returns a single value and can appear in SELECT, WHERE, ORDER BY, and inside aggregates.
  • If the ELSE clause is omitted and no condition matches, CASE returns NULL.
  • Simple CASE tests equality only; searched CASE (WHEN condition THEN …) supports any boolean expression.
🔎 EXISTS / IN / ANY / ALL Rules
  • EXISTS short-circuits on the first match and is NULL-safe — prefer it over IN for correlated checks.
  • NOT EXISTS is always safer than NOT IN when the subquery column can contain NULLs.
  • > ANY = "greater than the minimum value"; > ALL = "greater than the maximum value".
❌ Illegal Operations
  • Do not use aggregate functions in WHERE — use HAVING.
  • Do not reference a SELECT alias in WHERE or HAVING.
  • Do not use NOT IN when the subquery or list may contain NULLs — use NOT EXISTS.
  • BETWEEN cannot take a subquery as one of its bounds.

05 Joins

Joins combine rows from two tables on a matching condition. Eleven flavours, but they all derive from how you treat matched vs unmatched rows on each side.

Sample data. employees(emp_id, name, dept_id) with one employee whose dept_id is NULL, and departments(dept_id, dept_name) with one department that has no employees. We join on dept_id.

The four standard joins

Anti & semi joins

INNER JOIN — rows that match on both sides

SQL · inner join
SELECT e.name, d.dept_name
FROM employees e
INNER JOIN departments d ON e.dept_id = d.dept_id;
-- Drops the NULL-dept employee AND the empty department.
Use cases
The default join — fact-to-dimension lookups where you only want rows present in both, e.g. orders enriched with valid customers.

LEFT JOIN (LEFT OUTER) — all left rows + matches

SQL · left join
SELECT e.name, d.dept_name
FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id;
-- Keeps every employee; dept_name is NULL for the one with no dept.
Use cases
"Keep all customers, show their order count (0 if none)." The workhorse for retention/coverage reports where unmatched left rows still matter.

RIGHT JOIN — all right rows + matches

Mirror of LEFT JOIN. Most teams rewrite RIGHT as LEFT by swapping table order, for readability. Keeps the empty department with NULL employee.

FULL OUTER JOIN — everything from both sides

SQL · full outer
SELECT e.name, d.dept_name
FROM employees e
FULL OUTER JOIN departments d ON e.dept_id = d.dept_id;
-- Returns matches + the NULL-dept employee + the empty department.
Use cases
Reconciliation: find rows present in either source — comparing two snapshots to spot inserts and deletes. MySQL lacks FULL OUTER; emulate with LEFT … UNION … RIGHT.

CROSS JOIN — Cartesian product

SQL · cross join
SELECT s.size, c.color
FROM sizes s CROSS JOIN colors c;     -- every size × every color
-- m rows × n rows = m*n rows. No ON clause.
Use cases
Generating combinations: a calendar spine × every store, size/colour matrices, building dense date grids to fill gaps.
Pitfall
A missing ON condition silently produces an accidental cross join — millions of rows and a runaway query. If a join result explodes, check the join key first.

SELF JOIN — a table joined to itself

SQL · self join (manager → employee)
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.emp_id;
Use cases
Hierarchies (employee→manager), finding pairs (two employees in the same dept), comparing a row to a previous row before window functions existed.

ANTI joins — rows with NO match

Not keywords in most SQL (they are first-class in Spark SQL as LEFT ANTI JOIN); elsewhere you express them with NOT EXISTS or an outer join + IS NULL filter.

SQL · anti joins
-- LEFT ANTI: employees with no matching department
SELECT e.* FROM employees e
LEFT JOIN departments d ON e.dept_id = d.dept_id
WHERE d.dept_id IS NULL;
-- equivalently:
SELECT e.* FROM employees e
WHERE NOT EXISTS (SELECT 1 FROM departments d WHERE d.dept_id = e.dept_id);

-- RIGHT ANTI: departments with no employees (swap sides)
-- FULL ANTI: rows unmatched on EITHER side
SELECT * FROM employees e
FULL OUTER JOIN departments d ON e.dept_id = d.dept_id
WHERE e.emp_id IS NULL OR d.dept_id IS NULL;

-- Spark SQL native:
SELECT * FROM employees LEFT ANTI JOIN departments USING (dept_id);
Use cases
Orphan detection, "customers who never ordered", incremental loads (new keys not yet in the target), data-quality FK validation.

SEMI JOIN — left rows that have a match, returning only left columns

SQL · semi join
-- "customers who placed at least one order" — no duplication, no order columns
SELECT c.* FROM customers c
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
-- Spark SQL native:
SELECT * FROM customers LEFT SEMI JOIN orders USING (customer_id);
Pitfall
Using INNER JOIN instead of a semi join duplicates left rows when the right side has many matches. EXISTS/SEMI JOIN returns each left row once.

NATURAL JOIN — auto-join on all same-named columns

SQL · natural join
SELECT * FROM employees NATURAL JOIN departments;  -- joins on dept_id automatically
Pitfall
Avoid in production. It silently joins on every identically named column; adding a column like created_at to both tables later can change the join keys and break results invisibly. Always write explicit ON (or USING).

Performance considerations

  • Join algorithms: Nested loop (small/indexed), Hash join (large equi-joins, no order needed), Merge join (both inputs sorted on the key). The optimizer picks based on size and indexes.
  • Index the join keys on both sides; an unindexed FK forces a full scan per probe.
  • Broadcast join in Spark SQL: ship the small table to every node to avoid a shuffle — huge speedup when one side is tiny.
  • Filter before joining so fewer rows enter the join; the optimizer often does this (predicate pushdown) but help it.
  • Beware fan-out: joining on a non-unique key multiplies rows and inflates downstream SUMs.
Interview · common join problems
  1. "Customers who never placed an order." Anti join / NOT EXISTS.
  2. "Each employee with their manager's name." Self join on manager_id = emp_id.
  3. "Departments with zero employees." departments LEFT JOIN employees … WHERE emp_id IS NULL.
  4. "Why does my SUM double after adding a join?" Fan-out from a one-to-many join; aggregate the many-side first in a subquery/CTE, then join.
  5. "INNER vs LEFT for a metric that should never lose rows?" LEFT, so unmatched dimension rows still appear (with NULLs handled by COALESCE).
Rules Summary — Joins
🔗 Structural Rules
  • Every join (except CROSS JOIN) requires an ON or USING clause — omitting it silently creates a Cartesian product.
  • Use explicit JOIN keywords (INNER JOIN, LEFT JOIN), never old comma-syntax (FROM a, b WHERE a.id = b.id).
  • USING (col) is shorthand when both tables share the exact same column name — it deduplicates the column in SELECT *.
  • Always qualify column names with table aliases in multi-table queries to prevent ambiguity errors.
📐 Behaviour Rules
  • INNER JOIN returns only matched rows — unmatched rows from either side are dropped.
  • LEFT JOIN always keeps all rows from the left table; unmatched right-side columns are NULL.
  • RIGHT JOIN mirrors LEFT JOIN — most teams rewrite it as LEFT JOIN by swapping table order.
  • FULL OUTER JOIN keeps unmatched rows from both sides (NULLs fill the missing side). Not supported in MySQL — emulate with LEFT … UNION ALL … RIGHT … WHERE left.key IS NULL.
  • CROSS JOIN has no ON clause and returns M × N rows — always intentional, never accidental.
⚠️ NULL & Fan-out Rules
  • A NULL join key never matches anything — rows with NULL in the join column are dropped by INNER JOIN.
  • One-to-many joins multiply left-side rows — a SUM after such a join will be inflated (fan-out). Aggregate the many-side first.
  • For "exists in the other table" checks, use EXISTS or a semi-join — not INNER JOIN — to avoid duplicate left rows.
  • Filtering on the right table's column in WHERE on a LEFT JOIN silently converts it to an INNER JOIN — move that condition to ON.
❌ Illegal Operations
  • Do not use NATURAL JOIN in production — it joins on all matching column names and breaks silently when columns are added.
  • Do not use NOT IN when the subquery column can contain NULLs — use NOT EXISTS (LEFT ANTI JOIN).
  • Do not add a WHERE filter on the right-side column of a LEFT JOIN — put it in the ON clause to preserve outer join behavior.
  • CROSS JOIN has no ON clause — adding one makes it equivalent to an INNER JOIN.

06 Set Operators

Set operators stack result sets vertically (joins go horizontally). Every branch must have the same number of columns with compatible types, matched by position.

INTERSECTRows in both A and BRemovedHigh

SQL · set operators
SELECT customer_id FROM orders_2023
UNION ALL                              -- keep all, fastest
SELECT customer_id FROM orders_2024;

SELECT customer_id FROM store_customers;

Interview
  1. "UNION vs UNION ALL?" UNION removes duplicates (extra sort); UNION ALL keeps them and is faster.
  2. "How to find rows in A but not B without EXCEPT (e.g. MySQL)?" LEFT JOIN … WHERE b.key IS NULL or NOT EXISTS.
  3. "Do set operators match columns by name or position?" By position — column names come from the first query.
Pitfall
ORDER BY applies to the whole combined result and goes only at the very end, not on individual branches. Mismatched column counts or incompatible types error out.
Rules Summary — Set Operators
📐 Structural Rules
  • Every branch of a set operation must return the same number of columns.
  • Column data types across branches must be compatible (or explicitly cast).
  • Column names in the result come from the first query's SELECT list — not from subsequent branches.
  • Set operators match columns by position, not by name.
📌 Placement Rules
  • ORDER BY applies to the entire combined result and goes only at the very end — not inside individual branches.
  • Parentheses around individual branches are allowed for clarity when branch-level logic requires it.
  • UNION removes duplicates (implicit sort/hash — expensive); UNION ALL keeps all rows (faster) — default to UNION ALL.
❌ Illegal Operations
  • Do not use ORDER BY inside an individual branch — only at the end of the full combined query.
  • INTERSECT and EXCEPT are not available in MySQL — use LEFT JOIN … WHERE key IS NULL or NOT EXISTS instead.
  • Mismatched column counts or incompatible types will cause a compile-time error.
  • Do not assume EXCEPT equals NOT IN with NULLs — EXCEPT handles NULLs set-theoretically (NULL rows are comparable).

🔤 Core String Rules
  • SQL string indexes are 1-based, not 0-based: SUBSTRING(str, 1, 3) starts at the first character.
  • CONCAT() with any NULL argument returns NULL — guard with COALESCE(col, '').
  • CONCAT_WS(sep, …) ignores NULL arguments entirely (unlike plain CONCAT).
  • String comparisons are case-sensitive in PostgreSQL by default; MySQL varchar columns depend on collation.
🔍 Filtering / Index Rules
  • Applying a function to a column in WHERE (LOWER(name) = 'x') disables the B-tree index on that column (non-sargable).
  • To make it sargable: create a functional index on LOWER(name), or normalize the data at insert time.
  • Leading wildcards in LIKE ('%foo') cannot use a B-tree index — consider a full-text index for prefix-agnostic patterns.
🧰 Function Behavior Rules
  • REPLACE, TRIM, UPPER/LOWER return computed values — they do not modify the stored data.
  • LENGTH returns character count; use OCTET_LENGTH for byte count in multi-byte encodings.
  • In MySQL, || is logical OR by default (not concatenation) — use CONCAT() instead.
❌ Illegal Operations
  • Do not use WHERE UPPER(col) = 'X' on a large indexed column without a functional index — it causes a full scan.
  • Do not use || for concatenation in MySQL without verifying the SQL mode.
  • Do not assume SUBSTRING(str, 0, n) is 0-based — start index 0 is treated as 1 in standard SQL.

ORDER BY month;

SELECT * FROM orders
WHERE order_date >= CURRENT_DATE - INTERVAL '30 days';

FROM customers;

Timezone handling

  • Store instants in UTC (TIMESTAMPTZ); convert at the edges for display.
  • PostgreSQL: order_ts AT TIME ZONE 'Asia/Kolkata'.
  • Snowflake: CONVERT_TIMEZONE('UTC','Asia/Kolkata', ts).
  • Daylight Saving means a day can be 23 or 25 hours — don't compute "days" by dividing seconds by 86400.
Pitfall
WHERE DATE(order_ts) = '2024-01-01' wraps the column in a function → no index use and a full scan. Use a half-open range: order_ts >= '2024-01-01' AND order_ts < '2024-01-02'.
Interview
  1. "All orders in March 2024 — write a sargable predicate." order_ts >= '2024-03-01' AND order_ts < '2024-04-01'.
  2. "Revenue by week." GROUP BY DATE_TRUNC('week', order_date).
  3. "Why prefer TIMESTAMPTZ for events?" One unambiguous instant, comparable across zones, DST-safe.
Rules Summary — Date & Time Functions
📅 Type & Storage Rules
  • Store all event timestamps as TIMESTAMPTZ (TIMESTAMP WITH TIME ZONE) in UTC — convert to local time only at display.
  • DATE, TIMESTAMP, and TIMESTAMPTZ are different types — implicit casts can cause silent timezone errors.
  • BETWEEN on dates is inclusive on both ends — for timestamps, use a half-open range: col >= start AND col < end.
📐 Sargability Rules
  • Never wrap a date column in a function in WHERE — it disables the index (non-sargable).
  • ❌ WHERE YEAR(order_date) = 2024 → ✅ WHERE order_date >= '2024-01-01' AND order_date < '2025-01-01'
  • ❌ WHERE DATE(order_ts) = '2024-01-01' → ✅ WHERE order_ts >= '2024-01-01' AND order_ts < '2024-01-02'
📏 Arithmetic Rules
  • Daylight Saving Time can make a day 23 or 25 hours — never compute "number of days" by dividing seconds by 86,400.
  • DATE_TRUNC truncates to the start of the period (e.g. first of the month), not the end.
  • DATEDIFF behavior varies by dialect — always check whether it returns full intervals or just the day-number difference.
  • Sorting by a string-formatted date (TO_CHAR output) will sort lexicographically — sort by the actual DATE/TIMESTAMP column instead.
❌ Illegal Operations
  • Do not apply any function to the date column in WHERE — rewrite as a sargable range predicate.
  • Do not compare TIMESTAMP columns to DATE literals without explicit casting in strict-mode databases.
  • Do not sort by a TO_CHAR-formatted date string — sort by the actual DATE/TIMESTAMP column.

09 Aggregations

Aggregates collapse many rows into one summary per group. Master GROUP BY, then the rollup family for sub-totals and grand totals in a single pass.

FunctionReturnsNULL handling
COUNT(*)All rowsCounts NULLs
COUNT(col)Non-null valuesSkips NULLs
COUNT(DISTINCT col)Unique non-null valuesSkips NULLs
SUM / AVGTotal / meanIgnores NULLs
MIN / MAXSmallest / largestIgnores NULLs
SQL · group by + having
SELECT dept_id,
       COUNT(*)              AS headcount,
       AVG(salary)           AS avg_salary,
       MAX(salary)           AS top_salary,
       COUNT(DISTINCT title) AS distinct_titles
FROM employees
GROUP BY dept_id
HAVING COUNT(*) >= 3
ORDER BY avg_salary DESC;
Pitfall
Every non-aggregated column in SELECT must appear in GROUP BY (strict in PostgreSQL/SQL Server/Snowflake). MySQL historically allowed selecting ungrouped columns and returned arbitrary values — a notorious silent-bug source. Also AVG ignores NULLs, so AVG(commission) differs from SUM(commission)/COUNT(*).

GROUPING SETS · ROLLUP · CUBE

Definition
Extensions that compute multiple grouping levels in one query. ROLLUP = hierarchical subtotals + grand total. CUBE = every combination of dimensions. GROUPING SETS = an explicit list of groupings.
SQL · rollup / cube / grouping sets
-- Subtotals per (region, product), per region, and grand total:
SELECT region, product, SUM(amount) AS revenue
FROM sales
GROUP BY ROLLUP (region, product);

-- Every combination: (region,product),(region),(product),()
SELECT region, product, SUM(amount) FROM sales GROUP BY CUBE (region, product);

-- Explicit chosen levels only:
SELECT region, product, SUM(amount) FROM sales
GROUP BY GROUPING SETS ((region, product), (region), ());

-- Identify the subtotal rows:
SELECT region, product, SUM(amount),
       GROUPING(region) AS is_region_total
FROM sales GROUP BY ROLLUP (region, product);

In subtotal/grand-total rows, the rolled-up column is NULL; use the GROUPING() function to distinguish a real NULL from a subtotal marker.

Interview
  1. "COUNT(*) vs COUNT(col) vs COUNT(1)?" COUNT(*) and COUNT(1) count all rows identically; COUNT(col) ignores NULLs.
  2. "Get region subtotals and a grand total in one query." GROUP BY ROLLUP(region).
  3. "Second highest salary per department." Window functions (see §12) — DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) then filter rank = 2.
Rules Summary — Aggregations
📊 GROUP BY Rules
  • Every non-aggregated column in SELECT must appear in GROUP BY (strict in PostgreSQL, Snowflake, SQL Server).
  • MySQL historically allowed selecting ungrouped columns — this produces arbitrary, unreliable values; avoid it.
  • You can GROUP BY a column that is NOT in SELECT.
  • You cannot use SELECT aliases in GROUP BY — repeat the full expression, or wrap in a CTE/subquery.
🔢 NULL Rules in Aggregation
  • COUNT(*) counts every row including NULLs; COUNT(col) skips NULLs.
  • SUM, AVG, MIN, MAX all silently ignore NULLs.
  • AVG(col) ≠ SUM(col) / COUNT(*) when NULLs exist — AVG ignores them, the division divides by total rows.
  • COUNT(DISTINCT col) ignores NULLs in the distinct count.
📌 HAVING Rules
  • HAVING is evaluated after GROUP BY and aggregation; WHERE is evaluated before.
  • Put conditions on individual rows in WHERE (faster); reserve HAVING for conditions on groups/aggregates.
  • HAVING without GROUP BY applies to the entire table treated as one group.
📋 ROLLUP / CUBE / GROUPING SETS Rules
  • Subtotal rows produced by ROLLUP/CUBE have NULL in the rolled-up column — use GROUPING(col) to distinguish a subtotal NULL from a real NULL.
  • ROLLUP(a, b) produces (a,b), (a), () — hierarchical subtotals from right to left.
  • CUBE(a, b) produces all combinations: (a,b), (a), (b), () — use when every cross-dimension total matters.
❌ Illegal Operations
  • Do not use aggregate functions in WHERE — use HAVING.
  • Do not reference SELECT aliases in HAVING — they are not yet computed at that stage.
  • Do not check subtotal rows with plain IS NULL on a ROLLUP column — use GROUPING(col) = 1 to reliably identify them.

10 Subqueries

A query nested inside another. The key distinction is whether it runs once (uncorrelated) or once per outer row (correlated).

TypeReturnsRunsUsed in
ScalarOne row, one columnOnceSELECT list, WHERE
Row / columnA list / setOnceIN, ANY, ALL
Table (derived)A result setOnceFROM
CorrelatedDepends on outer rowPer outer rowWHERE, EXISTS, SELECT
SQL · subquery flavours
-- Scalar: compare each salary to the company average
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- Derived table in FROM
SELECT dept_id, avg_sal
FROM (SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id) t
WHERE avg_sal > 60000;

-- Correlated: employees earning above their OWN dept average
SELECT e.name, e.salary
FROM employees e
WHERE e.salary > (SELECT AVG(e2.salary) FROM employees e2
                  WHERE e2.dept_id = e.dept_id);   -- references outer e

-- EXISTS / NOT EXISTS
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
IN vs EXISTS
  • IN materializes the subquery's value list, then checks membership — fine for small lists; breaks on NULLs with NOT IN.
  • EXISTS short-circuits on the first matching row and is NULL-safe — prefer it for correlated existence checks and always for the negative case (NOT EXISTS).
  • Modern optimizers often rewrite IN ↔ EXISTS to the same plan, so on small data the difference is mostly readability and NULL safety.
Pitfall
A scalar subquery that returns more than one row throws a runtime error. And correlated subqueries in the SELECT list can run once per row — convert to a join or window function if the row count is large.
Interview
  1. "Correlated vs uncorrelated subquery?" Uncorrelated runs independently once; correlated references the outer query and conceptually runs per outer row.
  2. "Why does NOT IN return no rows here?" A NULL in the subquery makes the predicate UNKNOWN for all rows — use NOT EXISTS.
  3. "Rewrite this correlated subquery as a join." Aggregate the inner table by the correlation key in a derived table, then join on it.
Rules Summary — Subqueries
🛠️ Structural Mechanics
  • Enclose every subquery in parentheses ().
  • Inner subqueries always execute first; the outer query executes last.
  • Subqueries must be independently valid SQL statements.
  • A scalar subquery that returns more than one row throws a runtime error.
📍 Clause-Specific Placement
  • WHERE with = / > / <: use a scalar (one-row, one-column) subquery only.
  • WHERE with IN / NOT IN: use a multi-row, single-column subquery.
  • WHERE with EXISTS / NOT EXISTS: subquery can return any columns — SELECT 1 is conventional.
  • FROM clause (derived table): the subquery must have a table alias.
  • SELECT list: must return exactly one row and one column per outer row.
⚠️ NULL & Safety Rules
  • NOT IN with a subquery that contains any NULL returns zero rows — the predicate becomes UNKNOWN for all rows. Always use NOT EXISTS instead.
  • EXISTS is NULL-safe and short-circuits on the first match — prefer it for correlated existence checks.
  • Correlated subqueries reference the outer query and run once per outer row — convert to a JOIN or window function when the outer table is large.
❌ Illegal Operations
  • Do not use ORDER BY inside a subquery (only meaningful with TOP/LIMIT, which is non-standard in most subqueries).
  • Do not use BETWEEN directly with a subquery as a bound.
  • Do not use a correlated scalar subquery in SELECT on a large table — it runs per row; convert to a JOIN or window function.

11 Common Table Expressions (CTE)

A WITH clause names a temporary result set you can reference like a table. CTEs make complex logic readable and enable recursion.

SQL · basic & chained CTEs
WITH dept_avg AS (
  SELECT dept_id, AVG(salary) AS avg_sal
  FROM employees GROUP BY dept_id
),
above AS (
  SELECT e.name, e.salary, d.avg_sal
  FROM employees e
  JOIN dept_avg d ON e.dept_id = d.dept_id
  WHERE e.salary > d.avg_sal
)
SELECT * FROM above ORDER BY salary DESC;

Recursive CTE

Definition
A CTE that references itself: an anchor member (the seed) UNION ALL a recursive member that builds on the previous iteration until it returns no new rows. Used for hierarchies and generating sequences.
SQL · org chart traversal
WITH RECURSIVE org AS (
  SELECT emp_id, name, manager_id, 1 AS lvl          -- anchor: top managers
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  SELECT e.emp_id, e.name, e.manager_id, o.lvl + 1   -- recursive step
  FROM employees e
  JOIN org o ON e.manager_id = o.emp_id
)
SELECT * FROM org ORDER BY lvl, name;

-- Generate a date spine
WITH RECURSIVE dates AS (
  SELECT DATE '2024-01-01' AS d
  UNION ALL
  SELECT d + INTERVAL '1 day' FROM dates WHERE d < DATE '2024-12-31'
)
SELECT d FROM dates;
Pitfall
Forgetting a termination condition in the recursive member → infinite loop (engines cap recursion depth and error out). SQL Server defaults to MAXRECURSION 100.

CTE vs subquery & performance

  • Readability: CTEs name steps; deeply nested subqueries become unreadable.
  • Reuse: a CTE can be referenced multiple times in the same query.
  • Materialization: some engines materialize a CTE (compute once, store), others inline it. PostgreSQL ≥12 inlines by default; force with MATERIALIZED / NOT MATERIALIZED. A materialized CTE referenced once can be slower than a subquery because the optimizer can't push predicates through it.
  • CTEs are not indexes or persisted objects — they live only for the statement.
Interview
  1. "When is a CTE better than a subquery?" When logic is multi-step, reused, or recursive, and for readability — not for raw speed.
  2. "Print the full management chain for an employee." Recursive CTE walking manager_id.
  3. "Can a CTE hurt performance?" Yes, if materialized it blocks predicate pushdown; check the plan.
Rules Summary — Common Table Expressions (CTE)
📝 Structural Rules
  • Declare CTEs before the main query using WITH; each CTE is named and separated by commas (only the last CTE omits the comma).
  • A CTE name is valid only within the single query block it is defined in — not reusable across separate queries.
  • A CTE can reference an earlier CTE in the same WITH clause, but not a later one.
  • CTEs are not persistent objects — they exist only for the duration of the single statement.
🔁 Recursive CTE Rules
  • Always include RECURSIVE in the WITH clause: WITH RECURSIVE cte AS (…).
  • Structure: anchor member (seed rows) UNION ALL recursive member (builds on previous iteration).
  • The recursive member must reference the CTE name exactly once.
  • Always include a termination condition — without one, most engines cap recursion depth and throw an error.
  • SQL Server default max recursion is 100; set OPTION (MAXRECURSION 0) to remove the cap (use carefully).
🏎️ Performance Rules
  • A CTE is not a physical table or index — it doesn't automatically speed things up.
  • PostgreSQL ≥12 inlines CTEs by default; force evaluation once with MATERIALIZED keyword.
  • A materialized CTE can be slower than an inline subquery because the optimizer can't push predicates through it.
  • Use temp tables (not CTEs) when the intermediate result is large and reused multiple times.
❌ Illegal Operations
  • Do not use ORDER BY inside a CTE definition (unless combined with LIMIT/FETCH to produce a defined ordered set).
  • The recursive member cannot use GROUP BY, HAVING, DISTINCT, UNION (must be UNION ALL), or window functions.
  • Do not reference a CTE from a separate query or stored procedure call — it is not a persistent object.

12 Window Functions

The single most tested topic for data engineers. A window function computes across a set of rows related to the current row — without collapsing them like GROUP BY does.

Definition
The OVER() clause defines a window: an optional PARTITION BY (reset per group), an optional ORDER BY (sequence within the partition), and an optional frame (which rows around the current one). Every input row is kept; a new column is added.
SQL · anatomy
function() OVER (
    PARTITION BY dept_id          -- split into independent windows
    ORDER BY salary DESC          -- order within each window
    ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW   -- frame
)

Aggregate windows — running & group totals

SQL · SUM / AVG / COUNT OVER
SELECT order_id, customer_id, order_date, amount,
  SUM(amount)  OVER (PARTITION BY customer_id ORDER BY order_date) AS running_total,
  AVG(amount)  OVER (PARTITION BY customer_id)                     AS cust_avg,
  COUNT(*)     OVER (PARTITION BY customer_id)                     AS cust_order_count,
  amount - AVG(amount) OVER (PARTITION BY customer_id)             AS vs_avg
FROM orders;

With ORDER BY in the window, an aggregate becomes a running total. Without it, it's the partition-wide total repeated on every row — handy for "share of total": amount / SUM(amount) OVER ().

  SELECT name, dept_id, salary,

Pitfall
For "Nth highest", ROW_NUMBER gives exactly one row per rank but breaks ties arbitrarily; RANK/DENSE_RANK keep tied rows together. Pick based on whether ties should share the position. You cannot put a window function in WHERE — wrap it in a CTE/subquery and filter the alias.

Value functions — LAG · LEAD · FIRST_VALUE · LAST_VALUE

SQL · period-over-period
SELECT month, revenue,
  LAG(revenue)  OVER (ORDER BY month)            AS prev_month,
  revenue - LAG(revenue) OVER (ORDER BY month)   AS mom_change,
  LEAD(revenue) OVER (ORDER BY month)            AS next_month,
  FIRST_VALUE(revenue) OVER (ORDER BY month)     AS first_month_rev
FROM monthly_revenue;

-- LAG with default + offset: compare to 12 months ago, default 0
LAG(revenue, 12, 0) OVER (PARTITION BY product ORDER BY month) AS yoy_base
Pitfall
LAST_VALUE surprises everyone: with the default frame (UNBOUNDED PRECEDING ... CURRENT ROW) it returns the current row, not the partition's last. Fix the frame: LAST_VALUE(x) OVER (ORDER BY d ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING).

Window frames — ROWS vs RANGE

Definition
The frame limits which rows feed the function relative to the current row. ROWS counts physical rows; RANGE includes all rows with the same ORDER BY value (logical/peer-based).
SQL · frames
-- 7-day moving average (previous 6 rows + current)
AVG(amount) OVER (ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

-- Running total from the start of the partition
SUM(amount) OVER (ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

-- Centered 3-row window
AVG(x) OVER (ORDER BY t ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING)

Frame bounds: UNBOUNDED PRECEDING, n PRECEDING, CURRENT ROW, n FOLLOWING, UNBOUNDED FOLLOWING.

Pitfall
With ORDER BY and duplicate keys, the default frame is RANGE … CURRENT ROW, which includes all peer rows with the same value — so a "running total" can jump. For deterministic running totals, specify ROWS explicitly.
Real-world use cases
  • Running totals / cumulative revenue and YTD metrics.
  • Month-over-month and year-over-year deltas (LAG).
  • Deduplication: keep the latest record per key (ROW_NUMBER … ORDER BY updated_at DESC, filter = 1) — core to SCD and CDC pipelines.
  • Sessionization: detect gaps with LAG, flag new sessions, cumulative-sum the flags.
  • Percent of total, moving averages, rank within cohort.
Interview · window classics
  1. "Nth highest salary per department" — DENSE_RANK + filter.
  2. "Running total of daily revenue" — SUM() OVER (ORDER BY day ROWS UNBOUNDED PRECEDING).
  3. "Each row's % of its group total" — x / SUM(x) OVER (PARTITION BY grp).
  4. "Month-over-month growth" — (rev - LAG(rev)) / LAG(rev).
  5. "Keep only the latest row per customer" — ROW_NUMBER() … ORDER BY ts DESC = 1.
  6. "Gaps and islands: consecutive login streaks" — subtract ROW_NUMBER() from the date to form a constant group key, then aggregate.
  7. "Median per group" — PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY x) or NTILE/ROW_NUMBER trick.
  8. "ROW_NUMBER vs RANK vs DENSE_RANK" — see the ties table above; this is asked constantly.
Best practice
Always specify an explicit frame when the result depends on it. Reuse a named window: … OVER w … WINDOW w AS (PARTITION BY dept_id ORDER BY salary DESC) to keep multiple functions consistent and DRY.
Rules Summary — Window Functions
📐 Syntax Rules
  • Every window function requires an OVER() clause — without it the function behaves as a regular aggregate.
  • OVER() with empty parentheses spans the entire result set as one window.
  • PARTITION BY divides rows into independent windows and resets the calculation for each group.
  • ORDER BY inside OVER defines ordering within each partition — separate from the query-level ORDER BY.
🖼️ Window Frame Rules
  • Default frame when ORDER BY is present: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
  • Default frame without ORDER BY: ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING (whole partition).
  • Use ROWS (not RANGE) for deterministic running totals — RANGE includes all peer rows with the same ORDER BY value.
  • LAST_VALUE with the default frame returns the current row, not the last row — always specify the full frame explicitly.
🏆 Ranking Function Rules
  • ROW_NUMBER(): always unique, even for tied values (arbitrary tiebreaking).
  • RANK(): tied rows share the same rank; next rank skips (gaps): 1, 1, 3.
  • DENSE_RANK(): tied rows share the same rank; no gaps: 1, 1, 2.
  • NTILE(n): distributes rows into n equal buckets; larger buckets come first when rows don't divide evenly.
  • Ranking functions do NOT accept a window frame clause.
📍 Placement Rules
  • Window functions can only appear in SELECT and ORDER BY — never in WHERE, GROUP BY, or HAVING.
  • To filter on a window function result, wrap in a subquery or CTE and filter on the alias.
  • Window functions run after GROUP BY/HAVING but before the final ORDER BY.
❌ Illegal Operations
  • Do not place window functions in WHERE or HAVING — wrap in a CTE/subquery first.
  • Do not use ROWS/RANGE frame clauses with ranking functions (ROW_NUMBER, RANK, DENSE_RANK, NTILE) — they don't support frames.
  • Do not rely on the default frame for LAST_VALUE — it returns the current row, not the partition's last. Always specify the frame.

16 Indexing

An index is a separate data structure that lets the engine find rows without scanning the whole table — the single biggest lever on read performance.

How indexes work — the B-tree

Definition
Most relational indexes are B-trees (balanced trees). The root and internal nodes hold key ranges and pointers; leaf nodes hold the keys in sorted order plus a pointer (row id) to the actual row. Lookups, range scans, and sorted reads all traverse from root to leaf in O(log n) — a handful of page reads instead of millions.

Index types

TypeWhat it isUse when
ClusteredTable rows physically stored in index order (one per table)Range scans on the key; the PK is clustered by default in SQL Server/MySQL-InnoDB
Non-clusteredSeparate structure pointing back to rowsSecondary lookup columns; many per table
CompositeIndex on multiple columns (a,b,c)Multi-column filters; leftmost-prefix rule applies
UniqueEnforces uniqueness + indexesNatural keys, dedup constraints
BitmapBit vectors per valueLow-cardinality columns in DW (Oracle); great for AND/OR of many flags
CoveringIndex that includes all columns a query needsAvoids touching the table at all ("index-only scan")
SQL · creating indexes
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);  -- composite
CREATE UNIQUE INDEX uq_cust_email ON customers (email);
CREATE INDEX idx_orders_status ON orders (status) INCLUDE (amount);      -- covering (SQL Server/PG)
CREATE INDEX idx_orders_lower_email ON customers (LOWER(email));         -- functional index
Leftmost-prefix rule
A composite index on (customer_id, order_date) can serve filters on customer_id, or customer_id + order_date — but not a filter on order_date alone. Order the columns by how you query them (equality columns first, then range).
Best practice
Index the columns in WHERE, JOIN, and ORDER BY of your hot queries. Keep predicates sargable (no functions/maths on the indexed column). Prefer composite/covering indexes for frequent multi-column queries. Drop unused indexes.
Pitfall · the trade-offs
Indexes speed reads but slow writes (every INSERT/UPDATE/DELETE maintains them) and consume storage. Over-indexing a write-heavy table hurts. Indexes on low-cardinality columns (e.g. boolean) are often useless. Functions/implicit casts on the column disable the index. Stale statistics make the optimizer ignore good indexes.
Interview
  1. "Clustered vs non-clustered?" Clustered defines physical row order (one per table); non-clustered is a separate pointer structure (many allowed).
  2. "Why didn't my index get used?" Non-sargable predicate, implicit cast, low selectivity, stale stats, or the optimizer judging a scan cheaper.
  3. "What's a covering index?" One that contains every column the query needs, enabling an index-only scan.
  4. "Column order in a composite index?" Equality/most-selective and most-filtered columns first; honour the leftmost-prefix rule.

17 Partitioning

Partitioning splits one logical table into physical chunks so the engine can skip the chunks a query doesn't need (partition pruning) and manage data by chunk.

SchemeSplits byTypical key
RangeValue rangesDates: one partition per month/day
ListDiscrete value setsRegion/country code

CompositeCombination (range + hash/list)Range by month, sub-hash by id
SQL · range partition (PostgreSQL)
CREATE TABLE orders (order_id BIGINT, order_date DATE, amount NUMERIC)
PARTITION BY RANGE (order_date);

CREATE TABLE orders_2024_01 PARTITION OF orders
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');

-- This query reads ONLY the January partition (pruning):
SELECT SUM(amount) FROM orders WHERE order_date >= '2024-01-01' AND order_date < '2024-02-01';
Partition pruning
When the query filters on the partition key, the optimizer eliminates non-matching partitions before reading. This is the whole point — a year of data scanned becomes one month.
Use cases
Time-series fact tables (prune by date), cheap data retention (drop an old partition instead of a slow mass DELETE), parallel loads, and partition-wise joins. In data lakes / Spark SQL, partitioning = folder layout (/dt=2024-01-01/) that prunes files.
Pitfall
Pruning only works if you filter on the partition key directly — wrapping it in a function (WHERE YEAR(order_date)=2024) defeats it. Too many tiny partitions add metadata overhead (the "small files problem" in lakes); too few defeat pruning. Choosing a partition key that doesn't match query patterns gives all of the cost and none of the benefit. Partition ≠ index — they're complementary.
Interview
  1. "Partitioning vs indexing?" Partitioning divides storage to skip whole chunks; indexing finds rows within data. Use both.
  2. "How would you store 5 years of event data for date-range queries?" Range-partition by day/month; queries prune to the relevant window; retention = drop partitions.
  3. "What kills partition pruning?" Filtering on a function of the key, or on a non-partition column.

18 Query Optimization & Performance Tuning

A query is a declaration of the result you want; the optimizer chooses how to get it. Tuning is the craft of giving the optimizer good information and not fighting it. This is the single most-tested area in senior data-engineering interviews.

Execution plans
The plan is the engine's chosen strategy: which indexes, join algorithms, and order. EXPLAIN shows the estimated plan; EXPLAIN ANALYZE runs it and shows actual rows and timings. Reading plans is the core diagnostic skill — you compare estimated vs actual rows to spot bad statistics, and you look for the expensive node.
SQL · reading a plan
EXPLAIN ANALYZE
SELECT d.dept_name, COUNT(*) AS headcount
FROM employees e
JOIN departments d ON d.dept_id = e.dept_id
WHERE e.hire_date >= '2024-01-01'
GROUP BY d.dept_name;

-- Read bottom-up. Watch for:
--   Seq Scan on a large table       -> missing/unused index
--   "rows=1" estimate, "rows=900k" actual -> stale statistics, run ANALYZE
--   Nested Loop over many rows      -> wrong join algorithm
--   Sort / Hash spilling to disk    -> work_mem too low

Predicate pushdownPushes WHERE filters down to the scan / storage layerFewer rows ever leave storage; central to columnar & lake engines
Filter earlyReduce rows before joins/aggregations, not afterEvery downstream operator processes less data
Projection pruningRead only needed columns (avoid SELECT *)Less I/O, esp. columnar; enables covering indexes

Join optimization
Three physical algorithms: nested loop (great when one side is tiny or indexed), hash join (best for large unsorted equi-joins), merge join (best when both inputs are already sorted on the key). In distributed engines (Spark SQL), the big decision is broadcast (small dimension shipped everywhere) vs shuffle/sort-merge (both sides repartitioned by key). Broadcasting a small dimension table avoids a shuffle and is often a 10× win.
SQL · broadcast hint (Spark)
-- Force the small dimension to be broadcast, skipping the shuffle:
SELECT /*+ BROADCAST(d) */ f.*, d.dept_name
FROM fact_sales f
JOIN dim_department d ON d.dept_id = f.dept_id;
Statistics & ANALYZE
The optimizer is only as good as its row-count and distribution estimates. After big loads, refresh stats: ANALYZE orders; (PostgreSQL), UPDATE STATISTICS (SQL Server), ANALYZE TABLE ... COMPUTE STATISTICS (Spark SQL/Hive). Stale stats are the #1 cause of a plan that "suddenly went bad."
Caching
Result caches (Snowflake returns identical queries instantly), buffer/page caches (hot data in RAM), and materialized views (precomputed results) all trade storage/freshness for speed. In Spark, df.cache() pins a reused DataFrame in memory across actions.
Anti-patterns that kill performance
  • Non-sargable predicates — WHERE YEAR(order_date)=2024 or WHERE UPPER(name)='X' wrap the column in a function and disable the index. Rewrite as a range: order_date >= '2024-01-01' AND order_date < '2025-01-01'.
  • Implicit casts — comparing an indexed VARCHAR to a number casts every row.
  • SELECT * in production — reads & ships columns you don't need; breaks covering indexes.
  • Leading-wildcard LIKE '%foo' — can't use a B-tree index.
  • DISTINCT as a band-aid for a join that fans out — fix the join instead.
  • OR across different columns — often prevents index use; UNION ALL of two sargable queries can be faster.
  • Row-by-row scalar UDFs / cursors — replace with set-based SQL.
  • Correlated subquery in SELECT run per row — convert to a join or window function.
Interview
  1. "A query got slow overnight. Walk me through your diagnosis." Reproduce → EXPLAIN ANALYZE → compare estimated vs actual rows → check for seq scans, spills, stale stats → check whether data volume or plan changed → refresh stats / add or fix index / rewrite predicate.
  2. "What makes a predicate sargable?" The column appears bare on one side so the engine can seek the index; no function wrapping, no implicit cast, no leading wildcard.
  3. "When would you broadcast vs shuffle a join?" Broadcast when one side fits comfortably in memory; shuffle/sort-merge when both sides are large.
  4. "How do you optimize COUNT(DISTINCT) on a huge table?" Approximate counts (APPROX_COUNT_DISTINCT / HyperLogLog), pre-aggregation, or partitioned roll-ups.

19 SQL for Data Warehousing

Warehousing reshapes normalized operational data into models built for analytics: a few big fact tables of measurements surrounded by dimension tables of descriptive context. This dimensional modelling vocabulary is mandatory for any DE or analytics-engineering interview.

Fact vs dimension tables
A fact table stores numeric, additive measures (amount, quantity) at a defined grain (one row per order line), plus foreign keys to dimensions. A dimension table stores the descriptive "who / what / where / when" you slice and filter by (customer, product, date, geography). Facts are tall and thin; dimensions are short and wide.
Star vs snowflake schema
A star schema keeps each dimension as a single denormalized table joined directly to the fact — simple, fast, fewer joins. A snowflake schema normalizes dimensions into sub-tables (e.g. product → category → department) — less redundancy, more joins, more complexity. Stars win for query speed and simplicity; snowflakes save space and ease dimension maintenance.
SQL · classic star-schema query
SELECT  d.year, d.month, p.category, SUM(f.amount) AS revenue
FROM    fact_sales      f
JOIN    dim_date        d ON d.date_key    = f.date_key
JOIN    dim_product     p ON p.product_key = f.product_key
JOIN    dim_customer    c ON c.cust_key    = f.cust_key
WHERE   c.country = 'IN'
GROUP BY d.year, d.month, p.category
ORDER BY d.year, d.month, revenue DESC;
Surrogate keys
A surrogate key is a meaningless, system-generated integer (or hash) primary key for a dimension row — independent of the source's natural/business key. Why: it decouples the warehouse from source-system changes, gives compact fast joins, and — critically — lets one business entity have multiple dimension rows over time (the basis of SCD Type 2).
Slowly Changing Dimensions (SCD)
How you handle attribute changes (a customer moves city):
  • Type 1 — overwrite. Replace the old value; no history. Simple, but you lose the past.
  • Type 2 — add a new row. Keep the old row, insert a new versioned row with the new value, and track validity with effective_date, end_date, and an is_current flag (and a new surrogate key). Full history; the standard for audited warehouses.
SQL · SCD Type 2 with MERGE
-- 1) Expire the current row when the tracked attribute changed
MERGE INTO dim_customer t
USING staging_customer s
   ON t.cust_nk = s.cust_nk AND t.is_current = TRUE
WHEN MATCHED AND (t.city <> s.city OR t.tier <> s.tier) THEN
  UPDATE SET t.end_date = CURRENT_DATE - 1, t.is_current = FALSE;

-- 2) Insert the new version (new surrogate key) for changed + brand-new keys
INSERT INTO dim_customer (cust_sk, cust_nk, city, tier, effective_date, end_date, is_current)
SELECT nextval('cust_sk_seq'), s.cust_nk, s.city, s.tier, CURRENT_DATE, DATE '9999-12-31', TRUE
FROM   staging_customer s
LEFT JOIN dim_customer t
  ON t.cust_nk = s.cust_nk AND t.is_current = TRUE
WHERE  t.cust_nk IS NULL          -- new customer
   OR  t.city <> s.city OR t.tier <> s.tier;   -- changed attribute
Best practice
Conform dimensions (one shared dim_date, one dim_customer) so facts join consistently. Declare the fact grain explicitly and never mix grains. Keep facts additive; store semi-additive measures (balances) carefully.
Pitfall
Joining a fact to a Type-2 dimension on the natural key fans out across all historical versions — you must join on the surrogate key captured at load time, or filter is_current = TRUE for "as-is" reporting. Forgetting this double-counts revenue.
Interview
  1. "SCD Type 1 vs Type 2 — when to use each?" Type 1 when history is irrelevant (correcting a typo); Type 2 when you must report metrics "as they were" at a point in time.
  2. "Why surrogate keys?" Stability against source changes, compact joins, and enabling Type-2 versioning.
  3. "Fact-table grain?" The precise meaning of one row; defining it first prevents double counting.
  4. "Star vs snowflake trade-off?" Query speed/simplicity vs storage/normalization.

20 Advanced SQL

The power tools: reshaping rows↔columns, walking hierarchies, generating SQL at runtime, set-based upserts, and querying semi-structured JSON/array data — increasingly the day-to-day of modern data engineering.

PIVOT / UNPIVOT
PIVOT rotates rows into columns (long → wide), e.g. months become columns. UNPIVOT does the reverse (wide → long), which is usually what you want before loading a tidy fact table.
SQL · pivot — portable (CASE) and native
-- Portable: conditional aggregation works everywhere
SELECT customer_id,
       SUM(CASE WHEN status='shipped'   THEN amount END) AS shipped,
       SUM(CASE WHEN status='cancelled' THEN amount END) AS cancelled
FROM orders
GROUP BY customer_id;

-- Native PIVOT (SQL Server / Snowflake / Spark)
SELECT * FROM orders
PIVOT (SUM(amount) FOR status IN ('shipped','cancelled','pending'));
Recursive queries
A recursive CTE walks hierarchies (org charts, BOMs, graph paths) or generates sequences. Anchor member + recursive member UNION ALL, terminating when the recursive part returns no rows.
SQL · recursive — management chain
WITH RECURSIVE chain AS (
  SELECT emp_id, name, manager_id, 1 AS lvl
  FROM employees WHERE emp_id = 42            -- anchor: start person
  UNION ALL
  SELECT e.emp_id, e.name, e.manager_id, c.lvl + 1
  FROM employees e JOIN chain c ON e.emp_id = c.manager_id
)
SELECT * FROM chain;                          -- 42 and every manager above
MERGE / upserts
One statement to insert new rows and update existing ones — the heart of incremental loads. (Full syntax in §3.) Where MERGE is unavailable, use PostgreSQL INSERT … ON CONFLICT DO UPDATE or MySQL INSERT … ON DUPLICATE KEY UPDATE.
Dynamic SQL
SQL text assembled and executed at runtime — for variable table names, optional filters, or generated pivots. Powerful but the classic injection vector.
SQL · dynamic (PostgreSQL PL/pgSQL)
EXECUTE format('SELECT count(*) FROM %I WHERE country = $1', tbl)
  INTO n USING p_country;        -- %I quotes the identifier; $1 is bound, not concatenated
Pitfall
Never string-concatenate user input into dynamic SQL — that is SQL injection. Use parameter binding (USING / placeholders) and identifier-quoting functions (%I, QUOTENAME).
JSON functions
Query semi-structured data without a fixed schema. PostgreSQL: ->, ->>, jsonb_path_query. Snowflake: col:path::type, FLATTEN. Spark: get_json_object, from_json, explode.
SQL · JSON extraction
-- PostgreSQL: pull a scalar out of a JSONB column
SELECT payload->>'event_type'              AS event_type,
       (payload->'props'->>'amount')::numeric AS amount
FROM events
WHERE payload->>'event_type' = 'purchase';

-- Snowflake: dot/bracket path + FLATTEN an array
SELECT v:user_id::int AS user_id, f.value:sku::string AS sku
FROM raw_events, LATERAL FLATTEN(input => v:items) f;
Array functions
Build, expand, and aggregate arrays. ARRAY_AGG collapses rows into an array; UNNEST/explode/FLATTEN expand an array into rows; element access, ARRAY_CONTAINS, CARDINALITY inspect them.
SQL · arrays
-- Collapse each customer's orders into one array
SELECT customer_id, ARRAY_AGG(order_id ORDER BY order_date) AS order_ids
FROM orders GROUP BY customer_id;

-- Expand an array back into one row per element (PostgreSQL)
SELECT customer_id, o AS order_id
FROM customer_orders, UNNEST(order_ids) AS o;
Interview
  1. "Pivot months into columns without native PIVOT." Conditional aggregation: SUM(CASE WHEN month='Jan' THEN amt END).
  2. "Flatten a JSON array of line items into rows." FLATTEN/UNNEST/explode + path extraction.
  3. "Why is dynamic SQL dangerous and how do you make it safe?" Injection; use bound parameters and identifier quoting.
  4. "Traverse a parent-child hierarchy." Recursive CTE with anchor + recursive members.

21 SQL Interview Preparation

A working bank of patterns and questions. Master the patterns below and most "new" problems become variations you've already solved. Each coding problem lists the pattern and a one-line approach — try it before reading the approach.

The 12 patterns that cover ~80% of SQL interviews
  1. Top-N per group — ROW_NUMBER() OVER (PARTITION BY g ORDER BY metric DESC) then filter = 1 (or <= N).
  2. Nth highest — DENSE_RANK then filter = N (handles ties), or OFFSET/LIMIT.
  3. Running / cumulative total — SUM() OVER (ORDER BY … ROWS UNBOUNDED PRECEDING).
  4. Period-over-period — LAG()/LEAD() to compare to prior row, then (cur-prev)/prev.
  5. Gaps & islands — row_number trick: subtract a sequence from the value to group consecutive runs.
  6. Find duplicates — GROUP BY key HAVING COUNT(*) > 1.
  7. Records present in A not B — LEFT JOIN … WHERE b.key IS NULL (anti-join) or EXCEPT.
  8. Pivot / conditional aggregation — SUM(CASE WHEN … THEN …).
  9. Self-join — pairs, hierarchies, "find employees earning more than their manager."
  10. Median / percentiles — PERCENTILE_CONT or NTILE.
  11. Consecutive events — LAG/date diff, "N logins in a row," "3 days streak."
  12. Deduplicate keeping latest — ROW_NUMBER … ORDER BY ts DESC keep = 1.

Top SQL coding problems & approaches

A representative set spanning the whole difficulty range. Solve first, then check the approach.

SQL · #1 Second-highest salary
SELECT MAX(salary) AS second_highest
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
-- General Nth: DENSE_RANK() OVER (ORDER BY salary DESC) then WHERE rnk = N
SQL · #2 Nth highest per department (top-N per group)
SELECT * FROM (
  SELECT e.*, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS rnk
  FROM employees e
) t WHERE rnk <= 3;
SQL · #3 Employees earning more than their manager (self-join)
SELECT e.name AS employee
FROM employees e
JOIN employees m ON m.emp_id = e.manager_id
WHERE e.salary > m.salary;
SQL · #4 Duplicate emails
SELECT email, COUNT(*) AS n
FROM users GROUP BY email HAVING COUNT(*) > 1;
SQL · #5 Customers with no orders (anti-join)
SELECT c.customer_id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.customer_id IS NULL;
SQL · #6 Running total of daily revenue
SELECT order_date,
       SUM(amount) AS daily,
       SUM(SUM(amount)) OVER (ORDER BY order_date
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running
FROM orders GROUP BY order_date ORDER BY order_date;
SQL · #7 Month-over-month growth %
WITH m AS (
  SELECT DATE_TRUNC('month', order_date) AS mth, SUM(amount) AS rev
  FROM orders GROUP BY 1)
SELECT mth, rev,
       ROUND(100.0*(rev - LAG(rev) OVER (ORDER BY mth))
             / LAG(rev) OVER (ORDER BY mth), 1) AS mom_pct
FROM m ORDER BY mth;
SQL · #8 Median salary (percentile)
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median_salary
FROM employees;
SQL · #9 Consecutive-days streak (gaps & islands)
WITH d AS (
  SELECT DISTINCT user_id, login_date,
         login_date - (ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date))::int AS grp
  FROM logins)
SELECT user_id, MIN(login_date) AS streak_start, COUNT(*) AS streak_len
FROM d GROUP BY user_id, grp HAVING COUNT(*) >= 3;
SQL · #10 Deduplicate, keep latest record
WITH r AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY natural_key ORDER BY updated_at DESC) AS rn
  FROM staging)
SELECT * FROM r WHERE rn = 1;
SQL · #11 Department with highest average salary
SELECT dept_id, AVG(salary) AS avg_sal
FROM employees GROUP BY dept_id
ORDER BY avg_sal DESC LIMIT 1;
-- Ties-safe: rank the averages and keep rnk = 1
SQL · #12 Pivot order counts by status
SELECT customer_id,
       COUNT(*) FILTER (WHERE status='shipped')   AS shipped,
       COUNT(*) FILTER (WHERE status='pending')   AS pending,
       COUNT(*) FILTER (WHERE status='cancelled') AS cancelled
FROM orders GROUP BY customer_id;     -- FILTER is ANSI; CASE works everywhere
Top theory questions — rapid-fire answers
  1. WHERE vs HAVING? WHERE filters rows before grouping; HAVING filters groups after aggregation.
  2. DELETE vs TRUNCATE vs DROP? Row-level + WHERE + rollback; fast all-rows DDL; removes the object entirely.
  3. UNION vs UNION ALL? UNION dedups (sort cost); UNION ALL keeps all rows (faster) — default to ALL unless you need dedup.
  4. RANK vs DENSE_RANK vs ROW_NUMBER? Gaps after ties / no gaps / always unique sequential.
  5. Primary vs unique key? One PK, NOT NULL; many unique keys, allow one NULL (engine-dependent).
  6. Clustered vs non-clustered index? Clustered = physical row order (one per table); non-clustered = separate structure pointing to rows.
  7. INNER vs LEFT JOIN? Matches only vs all left rows + matches (NULLs where none).
  8. IN vs EXISTS? EXISTS short-circuits, better for large correlated subqueries; IN fine for small lists; beware NULLs with NOT IN.
  9. CTE vs subquery vs temp table? Readability / inline scope / materialized & indexable across statements.
  10. Normalization vs denormalization? Reduce redundancy (OLTP) vs reduce joins for read speed (OLAP).
  11. ACID? Atomicity, Consistency, Isolation, Durability.
  12. What is a sargable query? One that can use an index seek — no functions/implicit casts on the indexed column.
  13. SQL logical execution order? FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.
  14. Why can't you use a SELECT alias in WHERE? WHERE is evaluated before SELECT computes the alias.
  15. Materialized vs regular view? Stored precomputed result (must refresh) vs stored query re-run each time.
  16. SCD Type 1 vs Type 2? Overwrite (no history) vs versioned rows (full history).
Medium / hard window-function questions
  • 3-row moving average of daily revenue (ROWS BETWEEN 2 PRECEDING AND CURRENT ROW).
  • Each row's share of its group total (amount / SUM(amount) OVER (PARTITION BY g)).
  • First and last purchase per customer (FIRST_VALUE/LAST_VALUE with a full frame).
  • Sessionization: new session when gap since previous event > 30 min (LAG + cumulative SUM of a flag).
  • Top 3 products per category by revenue, ties included (RANK).
  • Days since the customer's previous order (LAG(order_date) + date diff).
  • Quartile each employee falls in by salary (NTILE(4)).
Join / CTE / optimization scenarios
  • Joins: overlapping date-range joins; "customers who bought A but not B" (anti-join); fan-out detection & fix; deduping a many-to-many before aggregating.
  • CTEs: recursive org chart with level + path; bill-of-materials explosion; generate a date spine to fill missing days before joining sparse facts.
  • Optimization scenarios: "This dashboard query takes 5 min — fix it." → check sargability, add covering index, pre-aggregate, partition-prune, broadcast the small dimension, refresh stats, replace correlated subquery with a window function.
Data-engineer interview patterns & FAANG-style themes
Beyond pure SQL, DE rounds probe: incremental/idempotent loads (MERGE, watermark columns), late-arriving data & backfills, deduplication strategy, SCD design, data-quality checks expressed as SQL (row counts, null ratios, referential checks), partitioning & file-size strategy in a lake, and translating a SQL transform into the Spark DataFrame API (next section). Product-company analytics rounds favor funnels, retention/cohorts, A/B metric computation, DAU/MAU, and "metric moved — why?" investigations — almost all built from window functions + conditional aggregation.
How to answer in the room
Clarify the schema and grain first. State your approach before typing. Name the pattern out loud ("this is top-N-per-group, so a windowed ROW_NUMBER"). Handle NULLs and ties explicitly. Finish by mentioning indexes/partitions that would make it fast at scale — interviewers love the performance coda.

22 SQL Best Practices Cheat Sheet

Habits that make queries correct, readable, and fast — and that signal seniority in code review and interviews.

Naming conventions
  • snake_case for tables and columns; lowercase, no spaces or reserved words.
  • Tables plural or collective (orders, order_items); columns singular (order_id).
  • Consistent key names: customer_id in every table that references it — never cust here and customerId there.
  • Prefix by layer in a warehouse: stg_, dim_, fact_, int_ (intermediate), mart_.
  • Booleans read as predicates: is_active, has_paid. Timestamps end in _at, dates in _date.
Formatting & readability
  • One major clause per line; keywords uppercase, identifiers lowercase.
  • Lead JOINs with explicit JOIN … ON — never comma-joins with WHERE conditions.
  • Qualify columns with table aliases in any multi-table query; use short meaningful aliases (o, c), not t1/t2.
  • Break complex logic into CTEs with descriptive names that read like a pipeline.
  • Comment the why, not the what; leave a header comment on non-obvious transforms.
SQL · readable vs cramped
-- Good: scannable, CTE-staged, aliased, explicit join
WITH recent_orders AS (
    SELECT customer_id, amount
    FROM   orders
    WHERE  order_date >= CURRENT_DATE - INTERVAL '30 days'
)
SELECT c.country,
       COUNT(*)        AS order_count,
       SUM(o.amount)   AS revenue
FROM   recent_orders o
JOIN   customers c ON c.customer_id = o.customer_id
GROUP BY c.country
ORDER BY revenue DESC;
Performance tips
  • Select only the columns you need; avoid SELECT * in production.
  • Filter as early as possible and keep predicates sargable (no functions on indexed columns).
  • Prefer UNION ALL over UNION unless dedup is required.
  • Prefer EXISTS over IN for large correlated checks; avoid NOT IN with nullable columns.
  • Replace correlated subqueries and self-joins with window functions where possible.
  • Index the columns you join and filter on; consider covering indexes for hot queries.
  • On big tables, partition by the common filter (usually date) and confirm pruning in the plan.
  • Refresh statistics after large loads; verify with EXPLAIN ANALYZE, don't guess.
Common mistakes
  • Comparing to NULL with = instead of IS NULL.
  • Assuming a default row order without ORDER BY.
  • Aggregating without realizing a join fanned out the rows (double counting).
  • WHERE on a LEFT JOIN's right-table column, silently turning it into an inner join.
  • Integer division truncating (1/2 = 0); cast first.
  • COUNT(column) vs COUNT(*) confusion with NULLs.
  • Mixing grains when joining facts to Type-2 dimensions on the natural key.
Industry standards
Keep transformations version-controlled and tested (dbt-style), make pipelines idempotent (re-running yields the same result — favor MERGE/overwrite-by-partition over blind INSERT), enforce data contracts and constraints where the engine supports them, and document the grain and meaning of every fact and dimension. Write queries assuming someone else will debug them at 2 a.m.

23 Data Engineer SQL Focus

The concentrated DE toolkit. Everything here was covered earlier — this section frames it the way pipelines and DE interviews actually use it, and pairs each core SQL idea with its PySpark DataFrame equivalent, since DEs constantly translate between the two.

What DE interviews weight most
Window functions, joins (incl. anti/semi & broadcast), CTEs, subqueries, set ops, partitioning, indexes, SCD 1&2, MERGE/upserts, query optimization, and the logical execution order — applied to real ETL: incremental loads, dedup, late data, backfills, and data-quality checks. If you're short on time, drill windows + joins + MERGE + optimization first.
SQL execution order — the mental model
FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT. This explains alias scope, why WHERE can't see aggregates, and where each operation's cost lands. Spark's Catalyst applies the same logical phases before physical planning.

filter · project · sort

SELECT customer_id, amount FROM orders
WHERE amount >= 100 ORDER BY amount DESC;

(orders
   .filter(orders.amount >= 100)

-- SQL
SELECT customer_id, SUM(amount) AS rev, COUNT(*) AS n
FROM orders GROUP BY customer_id HAVING SUM(amount) > 1000;

(orders.groupBy("customer_id")
       .agg(F.sum("amount").alias("rev"), F.count("*").alias("n"))

-- SQL

FROM employees e JOIN departments d ON d.dept_id = e.dept_id;

# PySpark
from pyspark.sql.functions import broadcast
employees.join(broadcast(departments), "dept_id", "inner") \

-- SQL
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.customer_id IS NULL;

# PySpark  (semi = present, anti = absent)
customers.join(orders, "customer_id", "left_anti")
window function — top-N per group / dedup
-- SQL
SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_date DESC) rn
  FROM orders) t WHERE rn = 1;

# PySpark
from pyspark.sql.window import Window
w = Window.partitionBy("customer_id").orderBy(F.col("order_date").desc())
orders.withColumn("rn", F.row_number().over(w)).filter("rn = 1")
running total
-- SQL
SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_date
                  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

# PySpark
w = (Window.partitionBy("customer_id").orderBy("order_date")
        .rowsBetween(Window.unboundedPreceding, Window.currentRow))
orders.withColumn("running", F.sum("amount").over(w))

-- SQL
WITH recent AS (SELECT * FROM orders WHERE order_date >= '2024-01-01')
SELECT country, SUM(amount) FROM recent r JOIN customers c USING (customer_id)
GROUP BY country;

# PySpark — each CTE is just an intermediate DataFrame

recent.join(customers, "customer_id").groupBy("country").agg(F.sum("amount"))

Real ETL scenarios (SQL-first)
  • Incremental load with watermark: pull only WHERE updated_at > :last_watermark, then MERGE into the target; store the new max watermark. Idempotent on re-run.
  • Dedup raw events: ROW_NUMBER() … ORDER BY ingested_at DESC, keep rn = 1 before MERGE.
  • Late-arriving / backfill: overwrite by partition (INSERT OVERWRITE … PARTITION(dt=…) / Spark dynamic partition overwrite) so reprocessing a day is safe and idempotent.
  • SCD Type 2 dimension: MERGE to expire changed current rows + insert new versions (see §19).
  • Date-spine fill: recursive CTE / generate_series to create every date, LEFT JOIN sparse facts so gaps become zeros.
  • Data-quality gates as SQL: assert row counts, null ratios, uniqueness of keys, and referential coverage; fail the pipeline if a threshold breaks.
SQL · idempotent incremental MERGE (the DE workhorse)
MERGE INTO fact_orders t
USING (
  SELECT * FROM (
    SELECT s.*, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) rn
    FROM   stg_orders s
    WHERE  s.updated_at > :last_watermark      -- only new/changed
  ) d WHERE rn = 1                              -- dedup to one row per key
) src
ON t.order_id = src.order_id
WHEN MATCHED THEN UPDATE SET amount = src.amount, status = src.status, updated_at = src.updated_at
WHEN NOT MATCHED THEN INSERT (order_id, customer_id, amount, status, updated_at)
                      VALUES (src.order_id, src.customer_id, src.amount, src.status, src.updated_at);
DE best-practice coda
Make every load idempotent, prune partitions on read, broadcast small dimensions, push filters to the source, keep MERGE keys indexed/clustered, and bake data-quality checks into the DAG. In interviews, always close with "and at scale I'd partition by date and broadcast the dimension" — it shows you think in systems, not just queries.
